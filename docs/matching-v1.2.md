# 都行 v1.2 匹配规则

## 唯一权威实现

`artifacts/api-server/src/lib/match-engine.ts` 是不依赖数据库、React 或随机数的纯函数模块。
`calculateMatch(participants, restaurant)` 计算单个候选；`rankCandidates` 排序；
`meal-recommendations.ts` 保存原有 24 家示例餐厅并选择推荐页。
数组算法支持 N≥2，包括 3～8 人；房间 API 和 UI 仍限制两人。

## 执行顺序

1. 少于两人不产生最终匹配。
2. 任何人的菜系 `avoid` 都直接排除整家餐厅，不能被加分抵消。
3. 排除超过最小有限预算等级或最小有限示例距离的餐厅。
4. 仅在数据明确说明不能调整辣度时，排除超过任意参与者辣度上限的候选。
5. 对剩余候选评分，然后按最低个人满意度、平均满意度、综合分、名称稳定排序。

现有预算为等级：1=¥（≤50参考区间）、2=¥¥（50–100参考区间）、3=¥¥¥（100+参考区间）。
比较预算等级，不将示例餐厅伪装成拥有精确人均报价。`unlimited` 不参与取最小值；
所有人不限时上限是 null，而不是人为设为某个数字。
相同的最小有限值函数也适用于将来真实金额上限，例如 100、80、50 得到 50；
当前接口没有增加真实金额模式。
所有距离相对于固定示例位置，不代表用户当前位置。

## 原始值、归一化与公式

菜系原始值：喜欢=2，可以=1，未选择=0；不想是过滤条件，不是负分。
个人菜系满意度 `s_i = 原始值 / 2`，范围 [0,1]。

- `min = min(s_i)`
- `avg = sum(s_i)/N`
- `agreement = 1 - (max(s_i)-min(s_i))`
- `CuisineScore = avg`
- `FairnessScore = min × agreement`
- `BudgetScore`：通过硬过滤后统一0.5，不因设置有限预算而加分。
- `DistanceScore`：通过硬过滤后统一0.5，不因设置有限距离而加分。
- `SpicyScore`：可调整性未知时0.5；明确兼容时，有限偏好1、随意0.5，取平均。

各维度已经归一化到 [0,1]。

```text
score = Math.round(100 × (
  0.30 × CuisineScore +
  0.30 × FairnessScore +
  0.15 × BudgetScore +
  0.15 × DistanceScore +
  0.10 × SpicyScore
))
```

分值确定且范围为0～100；按数学四舍五入为整数。
全部未知偏好、不限预算/距离时为20分，不会凭空出现高匹配。
当前所有示例餐厅缺少可靠辣度可调整信息，因此辣度维度中性，不声称完全符合。

采用**分层公平排序**，而非仅按总分：最低满意度优先保证每个人都有明确接受意愿，
再提高平均满意度，最后用综合评分决胜。
因此双方“可以”优先于一方“喜欢”另一方“未选择”，不会把沉默当强烈接受。
综合分是内部偏好评分，不是成功概率或真实满意率；排名也不是直接按显示分数排序。
结果卡片现标注“综合参考分”，卡片前明确说明公平优先、参考分不是排名分。

## 理由、分页与版本

理由直接由同一计算结果生成。全部喜欢、全部明确接受、部分未知分别采用不同文案；
预算/距离理由仅在存在实际限制且候选满足时出现；未知辣度只披露未知，不作兼容承诺。
前端直接显示后端 `matchScore` 和 `reasons`，不重算或根据餐厅名猜理由。

推荐每组最多3家，按索引0～2、3～5等递进，不循环到旧组；不足3家就显示实际数量。
没有下一组时禁用按钮并显示“暂时没有更多符合条件的推荐。”，API也以409拒绝继续翻页。
翻页只更新现有 `recommendationPage`，不改身份、偏好、版本或单店分数。
无候选时返回空数组，绝不自动放宽限制。

复用现有房间 `round` 作为对外 `preferenceRevision`，不新增数据库字段。
重选在事务中清除双方偏好和提交标记，round+1、推荐页归零。
任何已经提交过的参与者直接重新提交，也使旧轮失效：清除所有旧偏好，再保存当前人的新提交；
另一人必须提交新版本。请求必须带当前 revision，过期请求返回400。
因此旧版客户端需刷新应用后才能提交；现有房间与参与者不需要迁移。
缺少或格式不正确的版本号会收到易读的刷新提示，不再显示Zod字段错误。
前端提取服务端人类可读消息，过滤HTTP方法/路径前缀，并提供“刷新页面”操作。
重选之前先二次确认：双方已提交偏好和两端尚未提交的填写内容都会清空，双方需重新填写。
保留草稿再确认本次未实现：需要本人草稿读取、回填和版本语义，不能把旧提交直接当成本轮确认。

状态读取和提交/重选/换组均持有同一房间行锁，避免跨版本快照。
只有房间满两人、两人的提交标记存在且持久化偏好都有效时，后端才返回 revealed 和推荐。
前端通过2200ms轮询接收另一人的变化；双方提交前不泄露另一人的偏好。

## 小范围审查的评分案例

算法标识由 `fair-match-1` 升为 `fair-match-2`；权重和公平排序不变。
预算、距离通过过滤后都统一中性0.5，避免仅仅设置限制就奖励用户。

| 同一候选、相同菜系偏好 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 双方未选菜系、预算距离均不限 | 20 | 20 |
| 双方未选菜系、预算距离均有限且通过 | 35 | 20 |
| 双方喜欢、预算距离均不限 | 80 | 80 |
| 双方喜欢、预算距离均有限且通过 | 95 | 80 |

真实排序倒挂案例（修改前后均保留公平优先）：
三人对日料依次为喜欢、可以、可以，对中餐全部可以；其他属性相同且均不限。
日料最低满意度0.5、平均2/3、参考分48；中餐最低0.5、平均0.5、参考分50。
日料依然优先，因为平均接受度更高，不应为了分数单调而取消公平排序。
双人模型也可复现：日料喜欢/可以、辣度未知得50；
中餐可以/可以且明确可调整辣度、两人要求不辣得55，日料仍优先。
当前示例餐厅均未知辣度，在81种双人菜系组合中未发现倒挂；不是声称当前双人数据已经出现该问题。

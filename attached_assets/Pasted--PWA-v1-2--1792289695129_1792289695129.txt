你现在需要基于现有的「都行」PWA 项目，
完成 v1.2 版本迭代。

项目定位：

「都行」是一款帮助两个人快速决定
“今天吃什么”的多人决策应用。

它不是传统投票工具。

核心理念是：

让每个人独立表达真实偏好，
系统寻找所有人都能接受、
同时尽可能让大家满意的结果。

当前版本主要支持两人。

未来计划扩展到 3～8 人，
并逐步增加其他决策场景。

本次目标：

把当前简单推荐升级为：

公平、可解释、可测试、
能够扩展到 N 人的匹配算法。

================================
三、升级菜系偏好模型
================================

每个参与者对每个菜系
可以表达四种状态：

❤️ 喜欢
🙂 可以
🚫 不想
未选择

请统一其语义：

喜欢 = 2 分

可以 = 1 分

未选择 = 0 分

不想 = Hard Veto

注意：

“未选择”表示没有明显偏好，
不是拒绝。

Hard Veto 表示明确否决。

只要任意一名参与者
对某个菜系选择“不想”，

这个菜系下所有餐厅
都必须从候选结果中排除。

这个规则不能通过
其他人的高分抵消。

不能因为某个人特别喜欢，
就重新推荐被其他人否决的菜系。

否决检查应该发生在评分之前。

================================
四、设计公平匹配算法
================================

本次不能只按照
所有参与者的评分总和排序。

必须考虑：

1. 最低个人满意度
2. 整体平均满意度
3. 双方偏好一致程度
4. 预算兼容性
5. 距离兼容性
6. 辣度兼容性

核心理念：

优先找到所有人都能接受的选择，
再尽可能提高整体满意度。

例如：

情况 A：

用户 A：喜欢
用户 B：未选择

情况 B：

用户 A：可以
用户 B：可以

在其他条件相同的情况下，
优先推荐情况 B。

因为双方都有明确的接受意愿。

建议将评分拆分为：

CuisineScore
FairnessScore
BudgetScore
DistanceScore
SpicyScore

请设计明确、稳定、
容易解释的计算公式。

权重集中存放在一个配置文件
或算法模块中。

不要让多个页面
分别实现不同的评分逻辑。

================================
五、算法必须支持未来多人
================================

这是本次最重要的架构要求之一。

虽然目前 UI 只允许两个人，

但核心算法不能写死为：

userA
userB

禁止使用固定双人评分结构：

const score = userA.score + userB.score;

正确的设计方式应该是：

calculateMatch(
  participants,
  restaurant
)

其中：

participants 是数组。

算法应该遍历所有参与者：

- 检查所有人的否决项
- 计算所有人的满意度
- 计算最低满意度
- 计算平均满意度
- 检查所有人的预算
- 检查所有人的距离
- 检查所有人的辣度要求

最终返回统一的匹配结果。

要求：

1. 支持任意 N 个参与者。
2. N >= 2 时可以正常计算。
3. 未来扩展 3～8 人不需要重写算法。
4. 不要提前开放多人 UI。
5. 当前房间仍然限制最多两人。

请把核心匹配计算
封装为独立纯函数。

不要在 React 组件里
直接实现核心匹配算法。

================================
六、预算与距离硬性过滤
================================

预算和距离应当正确处理
所有参与者的限制。

例如：

A 最大预算：100 元
B 最大预算：50 元

最终有效预算：

50 元。

如果某个人选择不限，
则不增加限制。

如果所有人都选择不限，
则不产生预算上限。

多人情况下：

effectiveBudget =
所有有限预算上限中的最小值。

距离采用同样逻辑。

例如：

A 最远 5 km
B 最远 3 km

最终距离限制：

3 km。

effectiveDistance =
所有有限距离上限中的最小值。

任何超过明确预算或距离限制的餐厅，
都不能进入最终候选结果。

不能只是降低它们的分数。

注意：

当前如果采用 ¥、¥¥、¥¥¥，
请检查现有数据结构。

统一价格等级或金额区间的含义。

不要出现：

界面显示 ≤50，
实际算法却按照 ≤100 计算。

如果餐厅价格只有等级，
请使用一致的等级比较方式。

不要假装拥有不存在的精确价格数据。

另外：

当前模拟餐厅的 distance
如果是相对于固定示例位置的距离，
请在 UI 中明确说明它是示例距离。

不要把它描述成
用户当前位置的真实距离。

================================
七、辣度兼容性
================================

请检查现有辣度模型。

当前可能包含：

不辣
微辣
随意

请定义清晰规则。

例如：

如果参与者选择“不辣”，
就不应推荐明确要求高辣度、
且无法调整辣度的餐厅或菜品。

如果选择“随意”，
则不增加辣度限制。

注意：

餐厅整体辣度
不一定等于每道菜的辣度。

当前只是模拟数据，
不要实现过于复杂的菜品级匹配。

如果现有数据无法可靠判断
某餐厅是否可以提供不辣选择，

不要编造兼容性。

可以将辣度设为
中性或未知状态，
并且不要展示
“完全符合辣度要求”之类的理由。

================================
八、匹配度必须真实可计算
================================

这是第二个最重要的架构要求。

结果页显示的 0～100 分，
必须来自确定性的数学公式。

禁止：

- 写死 92%
- 随机生成百分比
- 根据排名直接赋分
- 第一名自动显示 100%
- 使用 AI 编造匹配分数
- 为了让推荐结果好看而人为加分

请明确实现：

1. 每个评分维度的原始分值
2. 每个评分维度的归一化方式
3. 每个维度的权重
4. 最终总分计算公式
5. 分数四舍五入规则
6. 硬性过滤的执行顺序

最终分数必须满足：

0 <= score <= 100

并且：

相同参与者偏好
+
相同餐厅数据
+
相同算法版本

必须得到完全相同的分数。

匹配度仅代表：

系统内部的偏好匹配评分。

不要将其描述成：

成功概率
满意概率
真实用户满意率

如果缺乏真实偏好信息，
不要生成没有依据的极高分。

为了避免用户误解，

结果页建议将：

“匹配度 92%”

调整为：

“匹配评分 92/100”

如果现有 UI 仍保留百分比，
也必须明确说明其为内部匹配评分，
不是统计概率。

================================
九、公平性算法要求
================================

请让公平性成为主要考虑因素之一。

不能出现：

一个参与者非常喜欢，
另一个参与者非常不满意，

但总分依然很高的情况。

推荐算法应兼顾：

最低满意度
+
平均满意度。

可以采用加权公式，
也可以使用分层排序方法。

建议优先考虑：

1. 排除明确否决
2. 满足预算和距离硬限制
3. 优先提高最低满意度
4. 再提高平均满意度
5. 最后考虑其他偏好与餐厅属性

请自行选择
一种简单且可解释的实现。

但必须在开发总结中写明：

为什么使用这种方法。

另外需要特别注意：

“未选择”不是明确接受。

例如：

双方都选择“可以”
应该优先于：

一方喜欢
另一方未选择。

不要把没有表达意见
直接当成强烈满意。

================================
十、动态推荐理由
================================

当前结果页可能已经有
推荐理由标签。

请让所有推荐理由
真正来自匹配数据。

不要写死理由。

例如：

如果所有人都喜欢日料：

❤️ 你们都喜欢日料

如果有人喜欢，
其他人可以接受：

🤝 有人很想吃，其他人也能接受

如果所有人都可以接受：

🙂 大家都能接受这个选择

如果预算满足：

💰 在大家的预算范围内

如果距离满足：

📍 符合大家的距离要求

如果辣度匹配：

🌶️ 符合大家的辣度偏好

注意：

不能出现：

某人否决日料，
结果却显示：

“你们都喜欢日料”。

推荐理由必须与评分结果一致。

推荐理由应当由
统一算法模块生成。

不要在前端通过
餐厅名称或排名猜测理由。

默认显示最重要的 2～3 个理由。

详细理由可以通过：

「为什么推荐？」

展开。

================================
十一、没有共同结果的情况
================================

必须处理无结果场景。

例如：

1. 所有菜系都被否决。
2. 所有餐厅超过预算。
3. 所有餐厅超过距离上限。
4. 预算和距离组合过于严格。
5. 没有足够的有效候选。

当没有任何有效候选时：

不能生成虚假的推荐。

显示空状态页面：

标题：

「看来今天有点难选 😅」

描述：

「暂时没有找到同时符合你们要求的选择。」

提供可能原因：

- 菜系限制过多
- 预算过低
- 距离范围过小

提供操作：

「重新调整偏好」

注意：

不能在用户不知道的情况下
偷偷放宽预算、
突破距离上限，
或者忽略否决项。

================================
十二、换一组推荐
================================

现有结果页包含：

「换一组推荐」

请确保该功能是真实有效的。

要求：

1. 保留所有参与者偏好
2. 不重新创建房间
3. 不清除参与者身份
4. 不修改原始偏好
5. 不突破硬性限制
6. 不重新加入被否决的菜系
7. 不重新计算随机匹配百分比

可以使用：

确定性的候选轮换策略。

例如：

第一次展示排序后的第 1～3 名。

第二次展示第 4～6 名。

第三次展示第 7～9 名。

如果候选数量不足，
则显示：

「暂时没有更多符合条件的推荐。」

不要在没有新候选时，
不断重复完全相同的推荐组合。

重要：

换推荐组只改变展示的候选。

不能改变餐厅的基础匹配评分。

同一家餐厅在偏好不变时，
每次显示的评分必须一致。

================================
十三、偏好重新提交

「重新选偏好」

功能。

不能继续向用户展示

只有当前房间中
全部参与者都完成本轮有效提交，
才能生成新的最终结果。

建议引入：

preferenceRevision

或者其他简单的版本机制。

目的是确保：

每次推荐对应一组明确的偏好版本。

请尽量复用现有房间状态结构。

不要为了这个功能
引入复杂的事件系统。

如果重新选择会影响所有参与者，
请在 UI 中明确提示。

前端不应重新计算评分。

如果项目已经采用其他合理架构，
可以沿用现有结构。

但必须确保评分口径唯一。
